# Sources allowed to write the process environment table directly, checked by
# `kin_core::test_env` tests::no_source_outside_the_sanctioned_guard_writes_the_environment.
#
# One workspace-relative path per line. An entry belongs here only when the write
# is product behavior. Test setup does not qualify: it goes through
# `kin_core::test_env::EnvVarGuard`, or the configuration is taken by argument.
#
# `crates/kin-core/src/test_env.rs` is the guard itself and is exempt in code.
#
# A line may also read `crates/<name> tests-only`, which exempts that crate's
# TEST code as a whole: its `tests/` binaries and its top-level `#[cfg(test)]`
# items, and nothing else. Product code in such a crate stays graded, and every
# other crate keeps exact-path semantics. It exists for one class only, a crate
# that sits BELOW kin-core and so cannot take `EnvVarGuard` as a dev-dependency,
# and it is narrower than the per-file form it replaces: a per-file line on a
# 7,500-line `src/lib.rs` would also excuse a future write in that file's
# product code, which is the write this scan exists to catch. Anything else
# shaped like `<something> tests-only` is refused rather than read as a path
# that matches nothing.

# `kin mcp start` binds the process to the daemon it resolved, and drops the pin
# when the workspace moves off the bound repository. The variable is the
# published interface the MCP daemon delegate reads, so the write is the feature.
crates/kin-cli/src/commands/mcp.rs

# `kin` and `kin-daemon` select their resource profile at startup when the
# operator set none, and `kin-daemon` additionally adopts the profile this
# repository recorded in its `[resources]` config so a knob set to survive an OOM
# is still in force on the restart that OOM causes (FIR-2504); an operator's own
# export outranks both. KIN_RESOURCE_PROFILE is the published interface kin-infer
# and kin-db read for the kernel plan, submission depth and embedding budgets, so
# writing it IS how a binary states its choice — there is no argument to pass it
# by across a registry dependency. The write happens in the first statement of
# each `main`, while the process is still single-threaded and before any reader
# caches its answer, and the precedence rule itself is a pure function
# (`product_default_for`) that tests exercise without touching the environment.
crates/kin-cli/src/resource_profile.rs

# `kin` and `kin-daemon` put Kin's own tool directories on `PATH` in the same
# single-threaded prologue, immediately after the `resource_profile` calls
# above. Language-server discovery is `which` over `PATH` and nothing else, so a
# server Kin downloaded and verified into its managed tool directory is
# reachable only if that directory is on the `PATH` of the process that starts
# enrichment, and the repo daemon inherits that environment from whichever `kin`
# command spawned it. `PATH` is the interface every `which` and every spawned
# tool already reads, so writing it IS how a binary publishes the tools it
# provisioned; there is no argument to pass it by across a process boundary. The
# managed directories are appended rather than prepended, so an operator's own
# toolchain still wins, and a second call is a no-op so a re-exec cannot grow
# `PATH` without end.
crates/kin-core/src/tool_prefix.rs

# The two imported crates that write the environment in their own tests, and a
# conscious exception rather than a precedent. Both are standalone publishable
# crates that sit below kin-core, so neither can take kin-core as a
# dev-dependency for `EnvVarGuard`, and both moved into `crates/` on 2026-09-11
# with their own test discipline. Product code in each stays graded.
#
# kin-vector: three test binaries, each setting KIN_VECTOR_SIMD before the
# library's OnceLock samples it once. These were three per-file lines when
# kin-vector landed; the crate-scoped form replaces them because it is the
# narrower statement, not the wider one. Follow-up: the three tests take the
# SIMD selection by argument, in a kin-vector pull request inside this
# workspace, and this line goes.
crates/kin-vector tests-only

# kin-infer: writes in `#[cfg(test)] mod tests` inside `src/lib.rs` and in three
# `tests/` binaries (the long-sequence Metal parity probe, the resident-stack
# parity probe and the sequence-length regression). A per-file line on that
# `src/lib.rs` would excuse every future write in 7,500 lines of product code.
# Follow-up: the probes take their configuration by argument, in a kin-infer
# pull request inside this workspace, and this line goes.
crates/kin-infer tests-only

crates/kin-db tests-only
